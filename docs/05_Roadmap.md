# Roadmap — 7 天執行時程

> **白話**：Roadmap 是「時間軸上的計畫」，每天要達到什麼里程碑、哪些是必須跑通的關卡。這是實際動工時每天早上看的那份文件。

---

## 全期概觀

```
Day 1 → 資料層打底（產區表、知識庫初稿）
Day 2 → 氣候 API 串接與快取
Day 3 → 距平計算 + 向量資料庫
Day 4 → 酒標辨識 + Tools schema
Day 5 → Agent 主流程串通（技術風險最高的一天）
Day 6 → 介面與視覺化
Day 7 → 驗證、打磨、文件
```

**關鍵原則**：Day 5 結束前必須有「端到端跑得通」的最小版本，即使醜也要能跑，之後兩天都是優化與加分項。

---

## Day 1 — 資料層打底

**里程碑**：資料檔案齊備，環境可跑

| 時段 | 任務 | 白話 |
|---|---|---|
| 上午 | T-01, T-02, T-03 環境設定 | 專案建好、套件裝好、API Key 讀得到 |
| 下午 | T-04 建立產區座標表 | 挑 10–15 個知名產區（波爾多、勃根地、香檳、加州納帕、澳洲巴羅莎、智利卡薩布蘭卡、紐西蘭馬爾堡、義大利托斯卡尼、西班牙里奧哈、日本山梨等），寫 JSON |
| 晚上 | T-05 知識庫（30-40%） | 開始寫氣候風味知識片段，每條 3–5 行 |

**當日產出**：能執行 `python -c "import openai; print('ok')"` 成功

**風險**：知識片段撰寫比想像慢，可以先寫核心的 15 條、剩餘明天補

---

## Day 2 — 氣候 API 串接

**里程碑**：能從 Open-Meteo 抓到真實資料

| 時段 | 任務 | 白話 |
|---|---|---|
| 上午 | T-05 完成知識庫 | 補到 30 條以上 |
| 下午 | T-06 Open-Meteo 呼叫函式 | 寫一個函式：輸入座標+日期 → 回傳每日氣候 |
| 晚上 | T-08 抓 30 年基準線 + 本機快取 | 為每個產區抓 1990–2020 資料，存本機 pickle/json，避免每次跑都打 API |

**當日產出**：`python fetch_climate.py --region "Bordeaux" --year 2019` 印出真實氣候

**檢核點**：抓下來的資料要人工看一眼，確認格式合理（例如波爾多 7 月不會是攝氏 -5 度）

---

## Day 3 — 距平計算 + 向量資料庫

**里程碑**：氣候能算出「量化異常程度」，知識能被檢索

| 時段 | 任務 | 白話 |
|---|---|---|
| 上午 | T-07 GDD 與距平計算 | 寫一個函式：輸入該年氣候+基準線 → 輸出「暖 12%、雨少 20%」 |
| 下午 | T-09 建 Chroma 向量庫 | 把知識片段用 embedding 轉向量存進去 |
| 晚上 | 測試檢索 | 用「偏暖偏乾」查詢，看能不能取回相關知識 |

**當日產出**：一份 `test_retrieval.py` 能證明檢索有效

**白話小補充**：
- **Embedding**：把文字變成一組數字（向量），意思相近的文字向量也相近
- **向量檢索**：用「意思相似度」找資料，不是關鍵字比對

---

## Day 4 — 酒標辨識 + Tools schema

**里程碑**：拍照能讀出結構化資訊，Tools 定義好

| 時段 | 任務 | 白話 |
|---|---|---|
| 上午 | T-10 Vision 酒標辨識 | 寫一個函式：輸入圖片 → 輸出「產區、酒莊、年份、品種」JSON |
| 下午 | 測試 Vision | 拿 5–10 張真實酒標照片測試（自己拍或網路找） |
| 晚上 | T-11 定義 5 個 Tools schema | 幫每個 tool 寫 OpenAI function calling 需要的 JSON schema |

**當日產出**：Vision 對清晰酒標辨識成功率能到 ≥ 70%

**風險提示**：花俏酒標、手寫字體可能讀不出來，這是預期內的，不要花太多時間調——手動輸入 fallback 就是為此存在

---

## Day 5 — Agent 主流程串通（最關鍵的一天）

**里程碑**：**端到端能跑**，即使沒 UI 也要能在 terminal 跑完整流程

| 時段 | 任務 | 白話 |
|---|---|---|
| 上午 | T-12 Agent orchestrator | 用 OpenAI function calling 讓 LLM 自主呼叫 tools |
| 下午 | T-12 除錯與整合 | 讓「輸入產區+年份 → 呼叫 tools → 拿到氣候與知識」跑通 |
| 晚上 | T-13 報告生成 prompt | 設計 system prompt 讓 LLM 生成有依據、有信心層級的報告 |

**當日產出**：Terminal 執行 `python agent.py --region "Bordeaux" --year 2019` 能印出一份完整風味推測報告

**如果卡住**：立刻退回「非 Agent」寫法——直接用 Python 串接呼叫（if/else 決定要呼叫哪個工具），先讓流程跑通再說。Agent 是加分項，能跑才是底線。

## 每日檢核（Definition of Done）

每天結束前問自己：

- [ ] 今天的關鍵里程碑達成了嗎？
- [ ] 有沒有把當日程式碼 commit 到 Git？
- [ ] 有沒有踩到雷需要在明天優先處理？
- [ ] 明天早上一睜開眼要做什麼，現在能一句話說出來嗎？

---

## 進度落後應變（Buffer 策略）

**如果 Day 3 結束沒跑通**：把 Day 6 的視覺化砍掉，只用 `st.write()` 純文字呈現
**如果 Day 5 結束 Agent 沒跑通**：退回直接函式呼叫，README 誠實寫「本次 v1 未使用 function calling，v2 計畫遷移」
**如果 Day 7 沒時間做驗證**：至少跑 1 個知名年份，寫進 README 當作「初步驗證，未來擴充」

**核心原則**：**寧可交出一個「完整但簡單」的 side project，也不要「複雜但半成品」**。面試展示時，能跑通的 demo 遠比華麗但當機的 demo 有說服力。

---

## 一週後（Day 8+）— 履歷投遞行動

1. 把 GitHub Repo 加到履歷 project 段落
2. 準備 3 分鐘口頭 demo 稿（對應 JD 的三大能力：Agent / RAG / 系統整合）
3. 準備「如果重做會怎麼改進」的答案（面試常見題）
4. 開始投遞
