關鍵節點警告：Day 5 是專案生死線

為什麼 Day 5 這麼重要？ T-12（Agent Orchestrator）是整個專案的匯流點——前四天所有準備工作（氣候 API、RAG、Vision、Tools Schema）都要在這天串聯成一個能自主運作的 Agent。如果 Agent 串不通，前四天的努力都無法對外展示。

當日底線：一定要達成端到端可執行——

python agent.py --region Bordeaux --year 2019

能印出完整風味推測報告，即使 UI 還沒做。

卡住怎麼辦：立刻退回「非 Agent」寫法——用 Python 直接串接呼叫（if/else 決定要呼叫哪個工具），先讓端到端跑通。Agent 是加分項，能跑才是底線。

Git 分支與 PR 流程

白話這張圖告訴你「未來每次開發新功能，Git 上要怎麼操作」。這個流程是業界標準 GitHub Flow。

Branching Flow
gitGraph commit id: "初始化專案" commit id: "加入 docs" commit id: "加入 CLAUDE.md" branch feature/T-06-open-meteo checkout feature/T-06-open-meteo commit id: "feat: 加入氣候 API" commit id: "test: 加入氣候測試" checkout main merge feature/T-06-open-meteo tag: "PR #1" branch feature/T-09-chroma checkout feature/T-09-chroma commit id: "feat: 建立向量資料庫" checkout main merge feature/T-09-chroma tag: "PR #2" branch feature/T-12-agent checkout feature/T-12-agent commit id: "feat: Agent orchestrator" commit id: "fix: 修正 tool routing" checkout main merge feature/T-12-agent tag: "PR #3"
分支命名規則
  • feature/<Backlog-ID>-<簡短描述>
  • 範例：feature/T-06-open-meteo-api
  • 範例：feature/T-12-agent-orchestrator
  • 範例：fix/T-14-mobile-camera-bug
PR 流程
  1. 從 main 拉新分支開發
  2. 完成後 push 到 GitHub
  3. 開 PR（Pull Request）回 main
  4. 自己 review 一次（重要！當自己的 reviewer）
  5. Merge 後刪除 feature 分支
