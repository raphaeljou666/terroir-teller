# User Story — 使用者故事

> **白話**：User Story 是「從使用者角度描述一個功能」的短句，格式是「作為 __，我想要 __，以便 __」。它比 PRD 更貼近實際使用感受，也是切分開發任務的基礎。

---

## 撰寫格式

```
作為 [某類使用者]，
我想要 [做某件事]，
以便 [達成某個目的]。

驗收條件：
- [ ] 條件 1
- [ ] 條件 2
```

---

## Epic 1：酒標辨識（輸入端）

### US-1.1 拍照上傳酒標

**作為** 剛買回一支酒的小雅，
**我想要** 用手機拍下酒標並上傳，
**以便** 不用自己打字輸入複雜的法文/義大利文/日文。

**驗收條件**：
- [x] Streamlit 頁面有「拍照」與「選擇檔案」兩個入口
- [x] 支援 JPG/JPEG/PNG 格式（本階段不支援 HEIC，見下方備註）
- [x] 檔案大小 ≤ 5MB
- [x] 上傳後立即顯示縮圖確認

> **範圍調整備註（T-10）**：原驗收條件含 HEIC，實作階段決定排除——HEIC 需要額外解碼依賴
> （`pillow-heif`），且非 JPG/PNG 的格式支援對 MVP 非必要，避免範圍蔓延（呼應
> CLAUDE.md 條款 10）。已於 CLAUDE.md 條款 27 同步標註覆寫。

---

### US-1.2 自動解析酒標資訊

**作為** 使用者，
**我想要** 系統自動抓出「產區、酒莊、年份、品種」四個關鍵欄位，
**以便** 不用自己判讀酒標。

**驗收條件**：
- [x] 呼叫 GPT-4o-mini Vision 完成辨識
- [x] 回傳結構化 JSON，包含四個欄位
- [x] 不確定的欄位標記為 `null` 而非猜測
- [x] 辨識時間 ≤ 5 秒

---

### US-1.3 手動修正辨識結果

**作為** 使用者，
**我想要** 在辨識結果不對時能手動修改任一欄位，
**以便** 不會因為 OCR 失誤導致整份報告錯誤。

**驗收條件**：
- [x] 每個欄位都是可編輯的輸入框
- [x] 修改後按「重新分析」會用新資訊重跑
- [x] 年份欄位有格式驗證（1940–當年）

## Epic 2：氣候資料處理（核心邏輯）

### US-2.1 產區座標查詢

**作為** 系統，
**我想要** 根據產區名稱查到對應的經緯度與所屬半球，
**以便** 呼叫氣候 API 並判斷生長季月份（南北半球相反）。

**驗收條件**：
- [x] 內建 10–15 個知名產區的座標對照表（實際 20 個，見 T-04 備註）
- [x] 對照表以 CSV 或 JSON 儲存，易於擴充
- [x] 找不到產區時，回傳明確錯誤訊息並建議手動輸入

---

### US-2.2 抓取歷史氣候資料

**作為** 系統，
**我想要** 呼叫 Open-Meteo API 抓某產區某年份生長季的每日氣候，
**以便** 計算風味相關指標。

**驗收條件**：
- [x] 呼叫 `archive-api.open-meteo.com/v1/archive` 成功
- [x] 取得每日最高溫、最低溫、降雨量
- [x] 生長季範圍：北半球 4–10 月、南半球 10–4 月
- [x] 網路失敗時能回傳明確錯誤

---

### US-2.3 計算氣候距平

**作為** 系統，
**我想要** 算出「這年比 30 年平均暖多少、雨多少」，
**以便** 量化該年的異常程度。

**驗收條件**：
- [x] 計算生長積溫（Growing Degree Days, GDD）
- [x] 計算生長季總降雨與採收前 30 天降雨
- [x] 對比 1991–2020 該產區同期均值，輸出距平百分比（WMO 標準 30 年平均期）

**白話**：
- **生長積溫（GDD）**：把每天超過某個基礎溫度（通常 10°C）的部分累加起來，數字越大代表「這年葡萄成熟得越充分」。這是釀酒界最常用的氣候指標。
- **距平**：跟長期平均的差距。例如「今年 GDD 比 30 年平均高 12%」代表這年偏暖。

## Epic 3：知識檢索與生成（RAG + LLM）

### US-3.1 建立氣候風味知識庫

**作為** 開發者，
**我想要** 把釀酒氣候學基礎知識向量化存進 Chroma，
**以便** Agent 能檢索到對應的知識片段輔助生成。

**驗收條件**：
- [x] 撰寫 30–50 條知識片段（如「積溫偏高 → 糖度成熟度可能較高、酸度可能較低」）（實際
      98 則，見 T-05 設計異動說明）
- [x] 每條包含：情境條件 + 對風味的影響 + 引用來源
- [x] 用 OpenAI `text-embedding-3-small` 向量化
- [x] 存進本機 Chroma 資料庫

---

### US-3.2 語意檢索對應知識

**作為** 系統，
**我想要** 根據計算出的氣候距平型態，檢索最相關的知識片段，
**以便** 生成有依據的風味推測。

**驗收條件**：
- [x] 將「偏暖 12%、降雨偏少 20%」等距平結果轉為查詢語句
- [x] 用向量相似度取回 Top-3 相關知識片段
- [x] 檢索結果會傳給 LLM 作為 context

---

### US-3.3 生成風味推測報告

**作為** 使用者，
**我想要** 收到一份白話、有依據、有信心層級的風味推測報告，
**以便** 決定是否開瓶或如何搭配。

**驗收條件**：
- [x] 報告包含：氣候摘要、風味推測、限制說明、資料來源（風味推測放最前，是使用者最關心的結論；氣候摘要是支撐證據，其後才是限制說明與資料來源）
- [x] 使用「可能傾向」等保留措辭，不用斷言句
- [x] 每段推測都對應知識庫引用（見 `04_Backlog.md` T-12／T-13 實作備註：GPT-4o-mini 的引用遵從度非 100%，程式端已處理「模型沒附引用」與「模型編造引用」兩種情況）
- [x] Markdown 格式輸出

## Epic 4：介面呈現（Streamlit）

### US-4.1 完整體驗流程

**作為** 使用者，
**我想要** 在一個頁面完成「上傳 → 查看報告」全流程，
**以便** 不需要來回切換。

**驗收條件**：
- [x] 單頁式流程：上傳 → 辨識結果確認 → 一鍵分析 → 報告呈現
- [x] 各階段有 loading 狀態提示，分析完成後狀態列收合，展開看得到走過哪幾步
- [x] 錯誤有明確訊息，不會白畫面
- [x] 報告分三層：風味推測直接可見，依據與說明各自收在一個區塊裡（T-24）

---

### US-4.2 氣候視覺化

**作為** 使用者，
**我想要** 看到該年氣候與 30 年平均的對比圖表，
**以便** 直觀理解「這年到底異常在哪」。

**驗收條件**：
- [x] 呈現每月均溫的該年 vs 平均對比（T-23 起改為畫兩者的差值，見下方備註）
- [x] 呈現每月降雨的該年 vs 平均對比（同上）
- [x] 使用 Streamlit 內建圖表或 Plotly

> **呈現方式調整備註（T-23）**：原驗收條件寫「每月均溫折線圖」與「每月降雨柱狀圖」，
> 各自並列該年與 30 年平均兩條序列。手機實測回饋認為兩張圖有點多餘、「取差異比較就好」，
> 因此改為單一的逐月距平圖：上排溫度、下排降雨，直接畫「該年減去 30 年平均」的差值，
> 橘色高於平均、藍色低於平均。**US-4.2 的目的（直觀理解這年異常在哪）沒有變，變的是達成
> 方式**——差值圖把原本要讀者自己在心裡相減的那一步直接畫出來。詳見 `04_Backlog.md` T-23。

---

### US-4.3 氣候比對表

**作為** 使用者，
**我想要** 一眼看到採收年的氣候跟平常差多少，
**以便** 不用理解「距平」是什麼也知道那一年反常在哪。

**驗收條件**：
- [x] 三列：生長季均溫、熱量累積（GDD）、生長季降雨
- [x] 採收年與 30 年平均並列，右欄給出差異
- [x] 均溫的差異用絕對值（`+1.2°C`），GDD 與降雨用百分比
- [x] GDD 附一句白話說明它是什麼
- [x] 算不出差異時顯示「無法計算」，不填 0 或推測值（條款 15）

> **為什麼均溫排第一列**：三個指標裡只有它有生活經驗錨點——看到 19.4°C 就知道那是什麼
> 感覺。GDD 的 1,580 沒有這種錨點，靠的是同一列的 30 年平均當對照。詳見
> `04_Backlog.md` T-24。

## Epic 5：驗證環節（履歷加分）

### US-5.1 知名年份對照測試

**作為** 開發者，
**我想要** 對 3–5 個公認的知名年份跑一輪測試，
**以便** 驗證系統推測方向與公開評論是否一致。

**驗收條件**：
- [x] 測試案例至少包含：2003 波爾多（熱浪）、2013 波爾多（多雨困難）、2018 加州（偏暖）
- [x] 每個案例記錄：系統輸出 vs 公開評論摘要
- [x] 產出「驗證報告」Markdown（`docs/07_ValidationReport.md`）。第一次驗證命中率 40–50%，
      未達 PRD 70% 門檻，如實記錄；根因（知識庫匯入時把規則的 `condition` 壓成 JSON 字串，
      導致氣候方向根本無從過濾）已於 T-21／T-22 修正，用同一套判準與來源重跑 5 案例後為
      **80%（嚴格）／90%（寬鬆），通過門檻**。兩份紀錄都保留在報告內，含當時對根因的錯誤
      判斷
