# User Story — 使用者故事

> **白話**：User Story 是「從使用者角度描述一個功能」的短句，格式是「作為 __，我想要 __，以便 __」。它比 PRD 更貼近實際使用感受，也是切分開發任務的基礎。

---

## 撰寫格式

```
作為 [某類使用者]，
我想要 [做某件事]，
以便 [達成某個目的]。

驗收條件：
- [ ] 條件 1
- [ ] 條件 2
```

---

## Epic 1：酒標辨識（輸入端）

### US-1.1 拍照上傳酒標

**作為** 剛買回一支酒的小雅，
**我想要** 用手機拍下酒標並上傳，
**以便** 不用自己打字輸入複雜的法文/義大利文/日文。

**驗收條件**：
- [ ] Streamlit 頁面有「拍照」與「選擇檔案」兩個入口
- [ ] 支援 JPG/JPEG/PNG 格式（本階段不支援 HEIC，見下方備註）
- [ ] 檔案大小 ≤ 5MB
- [ ] 上傳後立即顯示縮圖確認

> **範圍調整備註（T-10）**：原驗收條件含 HEIC，實作階段決定排除——HEIC 需要額外解碼依賴
> （`pillow-heif`），且非 JPG/PNG 的格式支援對 MVP 非必要，避免範圍蔓延（呼應
> CLAUDE.md 條款 10）。已於 CLAUDE.md 條款 27 同步標註覆寫。

---

### US-1.2 自動解析酒標資訊

**作為** 使用者，
**我想要** 系統自動抓出「產區、酒莊、年份、品種」四個關鍵欄位，
**以便** 不用自己判讀酒標。

**驗收條件**：
- [ ] 呼叫 GPT-4o-mini Vision 完成辨識
- [ ] 回傳結構化 JSON，包含四個欄位
- [ ] 不確定的欄位標記為 `null` 而非猜測
- [ ] 辨識時間 ≤ 5 秒

---

### US-1.3 手動修正辨識結果

**作為** 使用者，
**我想要** 在辨識結果不對時能手動修改任一欄位，
**以便** 不會因為 OCR 失誤導致整份報告錯誤。

**驗收條件**：
- [ ] 每個欄位都是可編輯的輸入框
- [ ] 修改後按「重新分析」會用新資訊重跑
- [ ] 年份欄位有格式驗證（1940–當年）

## Epic 2：氣候資料處理（核心邏輯）

### US-2.1 產區座標查詢

**作為** 系統，
**我想要** 根據產區名稱查到對應的經緯度與所屬半球，
**以便** 呼叫氣候 API 並判斷生長季月份（南北半球相反）。

**驗收條件**：
- [ ] 內建 10–15 個知名產區的座標對照表
- [ ] 對照表以 CSV 或 JSON 儲存，易於擴充
- [ ] 找不到產區時，回傳明確錯誤訊息並建議手動輸入

---

### US-2.2 抓取歷史氣候資料

**作為** 系統，
**我想要** 呼叫 Open-Meteo API 抓某產區某年份生長季的每日氣候，
**以便** 計算風味相關指標。

**驗收條件**：
- [ ] 呼叫 `archive-api.open-meteo.com/v1/archive` 成功
- [ ] 取得每日最高溫、最低溫、降雨量
- [ ] 生長季範圍：北半球 4–10 月、南半球 10–4 月
- [ ] 網路失敗時能回傳明確錯誤

---

### US-2.3 計算氣候距平

**作為** 系統，
**我想要** 算出「這年比 30 年平均暖多少、雨多少」，
**以便** 量化該年的異常程度。

**驗收條件**：
- [ ] 計算生長積溫（Growing Degree Days, GDD）
- [ ] 計算生長季總降雨與採收前 30 天降雨
- [ ] 對比 1991–2020 該產區同期均值，輸出距平百分比（WMO 標準 30 年平均期）

**白話**：
- **生長積溫（GDD）**：把每天超過某個基礎溫度（通常 10°C）的部分累加起來，數字越大代表「這年葡萄成熟得越充分」。這是釀酒界最常用的氣候指標。
- **距平**：跟長期平均的差距。例如「今年 GDD 比 30 年平均高 12%」代表這年偏暖。

## Epic 3：知識檢索與生成（RAG + LLM）

### US-3.1 建立氣候風味知識庫

**作為** 開發者，
**我想要** 把釀酒氣候學基礎知識向量化存進 Chroma，
**以便** Agent 能檢索到對應的知識片段輔助生成。

**驗收條件**：
- [ ] 撰寫 30–50 條知識片段（如「積溫偏高 → 糖度成熟度可能較高、酸度可能較低」）
- [ ] 每條包含：情境條件 + 對風味的影響 + 引用來源
- [ ] 用 OpenAI `text-embedding-3-small` 向量化
- [ ] 存進本機 Chroma 資料庫

---

### US-3.2 語意檢索對應知識

**作為** 系統，
**我想要** 根據計算出的氣候距平型態，檢索最相關的知識片段，
**以便** 生成有依據的風味推測。

**驗收條件**：
- [ ] 將「偏暖 12%、降雨偏少 20%」等距平結果轉為查詢語句
- [ ] 用向量相似度取回 Top-3 相關知識片段
- [ ] 檢索結果會傳給 LLM 作為 context

---

### US-3.3 生成風味推測報告

**作為** 使用者，
**我想要** 收到一份白話、有依據、有信心層級的風味推測報告，
**以便** 決定是否開瓶或如何搭配。

**驗收條件**：
- [ ] 報告包含：氣候摘要、風味推測、限制說明、資料來源
- [ ] 使用「可能傾向」等保留措辭，不用斷言句
- [ ] 每段推測都對應知識庫引用
- [ ] Markdown 格式輸出

## Epic 4：介面呈現（Streamlit）

### US-4.1 完整體驗流程

**作為** 使用者，
**我想要** 在一個頁面完成「上傳 → 查看報告」全流程，
**以便** 不需要來回切換。

**驗收條件**：
- [ ] 單頁式流程：上傳 → 辨識結果確認 → 一鍵分析 → 報告呈現
- [ ] 各階段有 loading 狀態提示
- [ ] 錯誤有明確訊息，不會白畫面

---

### US-4.2 氣候視覺化

**作為** 使用者，
**我想要** 看到該年氣候與 30 年平均的對比圖表，
**以便** 直觀理解「這年到底異常在哪」。

**驗收條件**：
- [ ] 呈現每月均溫折線圖（該年 vs 平均）
- [ ] 呈現每月降雨柱狀圖（該年 vs 平均）
- [ ] 使用 Streamlit 內建圖表或 Plotly

---

## Epic 5：驗證環節（履歷加分）

### US-5.1 知名年份對照測試

**作為** 開發者，
**我想要** 對 3–5 個公認的知名年份跑一輪測試，
**以便** 驗證系統推測方向與公開評論是否一致。

**驗收條件**：
- [ ] 測試案例至少包含：2003 波爾多（熱浪）、2013 波爾多（多雨困難）、2018 加州（偏暖）
- [ ] 每個案例記錄：系統輸出 vs 公開評論摘要
- [ ] 產出「驗證報告」Markdown，作為 README 的一部分
