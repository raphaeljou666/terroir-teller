# TerroirTeller（風土說書人）

> **一句話介紹**：拍下酒標，用該年份該產區的真實氣候資料，推測這瓶酒可能的風味走向，並解釋為什麼。
>
> **專案定位**：一週內完成的個人 side project，同時作為履歷作品，對應 104 上「Agentic AI × RAG × 系統整合」職缺方向。

---

## 為什麼叫 TerroirTeller

**Terroir（風土）** 是酒界核心術語，指一款酒的產地自然條件總和——氣候、土壤、地形。同一支酒不同年份為什麼喝起來不一樣？很大一部分就是 terroir 中「氣候」這個因子在作祟。

**Teller** 就是「說書人」，這個系統的角色不是評分，而是**把氣候資料翻譯成看得懂的風味故事**。

---

## 快速導覽（3 分鐘理解全貌）

**要解決的痛點**：市面上很多酒沒有中文品飲筆記，或者背標只寫行銷話術，看不出「為什麼這年份跟去年不一樣」。

**核心解法**：
1. 拍酒標 → GPT-4o-mini Vision 讀出產區/年份/品種
2. Agent 呼叫氣候 API 抓該年份該產區的真實氣候
3. 計算氣候距平（今年比 30 年平均暖多少、雨多少）
4. RAG 檢索釀酒氣候學知識，生成風味推測
5. 驗證環節：拿知名年份對比公開評論，確認方法論有效

**主要技術棧**：Python + OpenAI API（GPT-4o-mini + Vision + Embedding）+ Chroma 向量資料庫 + Open-Meteo 氣候 API + Streamlit 介面

## 技術架構

系統分兩個獨立階段呼叫 LLM，這是整個專案裡最值得說明的架構決定。

**階段一**是 `agent.py`，一個 tool-calling 迴圈，職責只有蒐集資料——呼叫酒標辨識、產區合法性檢查、氣候距平查詢、知識庫檢索這幾支 tool，system prompt 寫得短而機械化，只管「該呼叫哪個工具、資料夠不夠」。**階段二**是 `src/report.py`，另外發一次呼叫，把階段一蒐集到的距平數字與知識庫片段組成 context，交給專門寫報告的 prompt——這支 prompt 管的是四段式結構、保留措辭（「可能傾向」而非「絕對是」）、引用規則，還有一份拒答清單（醫療建議、酒款評分、陳年潛力精確預測等 10 項，見 `docs/04_Backlog.md` T-13）。

拆成兩支的理由很直接：tool-routing 要不要呼叫某個工具，跟報告寫得好不好讀，是兩種不同的 prompt engineering 問題。混在同一份 prompt 裡，兩邊的指令會互相稀釋。分開之後，兩份 prompt 都能各自聚焦、各自迭代，不用擔心改報告寫作規則會連帶影響工具呼叫的穩定度。

引用機制是另一個值得寫的細節。報告生成呼叫 OpenAI 的 Structured Outputs，把每段風味推測的 `cited_ids` 欄位用 `enum` 限定成「這一次實際檢索到的 chunk id」——不是靠模型自律「請務必引用真實來源」，而是在 schema 層就讓模型沒有辦法編出資料庫裡不存在的引用 id。這對應 `docs/01_PRD.md` 第 6 節「可解釋性 100% 有引用來源」這個成功指標，也是專案裡少數真正做到「結構上不可能出錯」而不是「靠 prompt 撐著」的部分。

## 氣候資料怎麼算

氣候資料全部來自 [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api)，底層是 ECMWF 的 ERA5 重分析資料集。免費、不需 API Key，每日彙總以 UTC 曆日計算。

生長季怎麼取決於半球：北半球是當年 4 月到 10 月，南半球跨年，從前一年 10 月到當年 4 月。所以 Mendoza 的 2019 年份指的是 2018-10 到 2019-04 這一季。

資料本身的空間解析度限制、基準線的偏差、代理指標的形狀問題，整理在下面「方法論與限制」一節。

```bash
# 查單一年份的生長季氣候
python -m src.climate --region "Bordeaux" --year 2019

# 抓 30 年基準線（第一次會打 API，之後讀 data/cache/）
python -m src.climate --region "Mendoza" --baseline

# demo 前一次預熱 20 個產區的基準線快取
python -m src.climate --warm-cache-all
```

一次基準線請求要抓 30 年的每日資料，權重不低。Open-Meteo 免費方案的每小時額度大約只夠 13–14 個產區，所以 `--warm-cache-all` 要分兩次跑，中間隔一小時；碰到額度上限時它會停手並把剩下的產區標成「未抓取」，不會傻等。抓好的快取放在 `data/cache/`（約 12MB，已排除在版本控制外），之後查詢不再打 API。

## 方法論與限制

這裡列的限制大部分來自 `docs/01_PRD.md` 第 7 節與開發過程中的踩雷紀錄，不是臨時湊的免責聲明。

**氣候只是影響風味的其中一個因子**。同一年份、同一產區，不同酒莊的採收時機、發酵溫度、橡木桶選擇都會讓成品差很多，這些系統完全看不到。報告推測的是「這年氣候條件傾向讓哪種風味走向更可能出現」，不是這支酒實際喝起來的樣子。

**氣候資料的空間解析度是 25 公里的網格**，一個網格點代表的是一整片區域的平均，不是某座葡萄園。地形破碎的產區受影響最明顯——Barolo、Central Otago、Marlborough 抓到的生長季降雨大約是實測站數值的兩倍，因為網格把附近山區的降雨算了進來。系統算的是距平（今年 vs 同一個網格點的 30 年平均），這種系統性偏差在相減時會抵消掉大半，「這年比平均濕兩成」這種結論還站得住腳，但網格算出來的絕對降雨量不該當成當地實測值來讀。

**30 年基準線本身已經被暖化墊高**。基準線用的是 WMO 標準的 1991–2020，這 30 年本身比更早期的基準線暖，所以算出來的距平值會偏保守——如果改用 1961–1990 當基準，同一年的暖異常會顯得更極端。

**採收前 30 天降雨是代理指標，不是真實採收日資料**。系統沒有任何一支酒的實際採收日期，只能用「生長季結束日往前推 30 天」估算。這在偏暖、早熟的年份會抓錯窗口——2019 與 2003 的 Bordeaux 實際採收都早於代理指標假設的日期，算出來的「採收前雨量」其實抓到的是採收之後才下的秋雨，兩案報告都一度把稀釋效應寫得比實際情況重（細節見下方「驗證結果」）。目前的處理方式是把這個指標在報告裡的權重降低、標註「參考價值有限」，不是修掉指標本身——要真的修需要真實採收日資料，目前沒有這個資料來源。

**產區覆蓋只有 20 個**，清單見 `data/regions.json`。實測時發現大部分真實酒標拍到的產區（Beaujolais、Chinon、Asti 都試過）不在清單內，系統會誠實告知「不涵蓋此產區」而不是硬套一個知識庫沒有的答案，但這代表能用的範圍目前還很窄。

## 驗證結果

`docs/07_ValidationReport.md` 完整記錄了驗證過程，這裡摘要重點，包含中間判斷錯的那一段。

第一輪驗證挑了 5 個氣候方向明確、有公開酒評可查證的年份（2003／2013／2019 Bordeaux、2018／2011 Napa Valley），把系統生成的報告拿去對照 Jancis Robinson、Wine Spectator 這類來源的年份摘要，看氣候方向（偏暖/偏冷、偏乾/偏濕）跟對應的風味走向對不對得上。結果是 2 個一致、1 個部分一致、2 個不一致，嚴格算法命中率 **40%**，沒有到 PRD 訂的 70% 門檻。

兩個不一致案例剛好都是偏冷年份——2013 Bordeaux 系統文字寫成「均溫偏高」，2011 Napa 的風味推測整段套用了偏暖規則，方向都跟系統自己算出來的 GDD 距平相反，也跟公開評論相反。當時的判斷是：這是語意檢索在小型知識庫下的排序問題，機率性的，沒有一行程式碼能保證修好，決定不動 `retrieval.py`，只把診斷過程記錄下來，留給後續評估。

這個判斷後來被推翻了。往下查知識庫的 metadata 匯入流程才發現，規則的 `condition.temperature`（該規則適用的氣候方向）在匯入時被整個 `json.dumps()` 成一個 JSON 字串塞進 metadata，Chroma 的 `where` 查詢語法沒辦法看進字串內部做過濾。方向從來就不是「排序排不準」，是**根本沒有在過濾**：不管查哪一年，10 則規則永遠都是候選，最終選哪則完全交給向量相似度，而查詢字串裡代表方向的訊號只有「高」「少」兩個字，很容易被產區名、年份這些字面相似的詞蓋過去。

修法是把 `condition` 底下的子欄位額外攤平成 `condition_temperature` 這種可以直接拿去 `where` 篩選的純量欄位，氣候方向不再讓模型用語意猜，改由 `climate.classify_gdd_direction()` 從 GDD 距平算出來後用程式碼強制注入、過濾。重新匯入知識庫，用同一批案例、同一套判準、同一批公開評論來源重跑一次，兩個不一致案例都翻正，嚴格命中率從 40% 升到 **80%**（4/5 一致、1 個部分一致，寬鬆算法 90%），通過 PRD 門檻。即使把唯一還沒到「一致」的 2019 Bordeaux 算成不一致，嚴格命中率仍是 80%——結論不靠那一案怎麼判撐著。

比起 80% 這個數字本身，中間那段判斷錯誤更值得記下來：第一次認定「機率性問題修不掉」是錯的，根因其實是一個決定性的、可以重現的資料匯入 bug。這個判斷錯誤沒有從報告裡刪掉，`docs/07_ValidationReport.md` 完整保留了兩次驗證的原始紀錄，包含當時那句後來被證明錯誤的診斷。

2019 Bordeaux 修正後仍是「部分一致」：陳年潛力的反向結論消失了、稀釋不再是全文主軸，但系統仍寫「酸度相對偏低、口感豐滿厚重」，而公開評論把酸度與新鮮感當成這個年份的招牌特徵，這個細節上的方向還是對不上。

## 刻意不做的事

比起功能清單，這些「決定不做」的判斷更能說明實際做過什麼考量。

**一鍵匯出報告（T-19）**：在 PRD 的加分功能清單裡，但核心消費動線是「輸入或辨識資訊 → 生成報告 → 使用者理解年份差異」，匯出一份 Markdown 檔不在這條線上——會想要檔案的是開發者或想轉貼的人，不是站在貨架前查酒的使用者。也評估過改成複製到剪貼簿的分享方式，但瀏覽器寫入剪貼簿（尤其是圖片）需要 HTTPS，跟下面移除 `st.camera_input()` 是同一個限制，純文字複製雖有舊式 fallback 但價值有限，整項擱置到之後部署到 HTTPS 環境再重新評估。

**`st.camera_input()`**：原規劃是拍照優先叫出手機相機，但這個元件需要瀏覽器安全情境（HTTPS 或 localhost）才能取得相機權限。手機連區網 IP 的 HTTP 網址測試時，瀏覽器直接擋掉相機存取，元件卡在權限請求畫面永遠打不開。改用 `st.file_uploader()`——手機瀏覽器的原生檔案選擇器本身就有拍照選項，拍照能力沒有真的消失，只是換了一個入口。

**HEIC 格式支援**：iPhone 預設存檔格式，原規劃要支援，但需要額外的 `pillow-heif` 依賴，對 MVP 不是必要條件，實作階段拿掉，只驗證 JPG/JPEG/PNG。

**降雨軸不做方向硬篩**：氣候知識庫的 10 則規則在「溫度 × 降雨」這個網格上有缺口，例如沒有「偏暖但降雨正常」這一類。如果溫度和降雨都用 `where` 硬過濾，像 2003 Bordeaux 這種生長季降雨距平只有 +0.0% 的年份，10 則規則會篩到只剩一則冰雹規則存活，反而打壞檢索。溫度方向做確定性硬過濾（這是驗證結果裡真正修掉的 bug），降雨方向維持軟訊號——寫進查詢字串，不做硬性排除。

**PRD 明訂的 Non-Goals**：不做即時通路庫存查詢、不做百萬酒款資料庫、不做風味斷言（只做「可能傾向」的保留推測）、不做使用者帳號與雲端儲存、不做行動裝置原生 App。這些不是漏掉，是一開始就沒有排進範圍。
